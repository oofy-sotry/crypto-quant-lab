# crypto-quant-lab 확장 로드맵 (v2)

7일 미니 프로젝트(`docs/PLAN.md`, v1)를 Python 백엔드·데이터 직무 전반에 내세울 대표 개인 프로젝트로 키운다.

```
데이터를 모으고(수집) → 맞는지 확인하고(정합성) → 계산하고(집계·재처리)
→ 빠르게 제공하고(API·튜닝) → 운영한다(관측성·자동화)
```

## 1. 원칙

- 단계마다 **실제로 동작하는 것 + 측정값 + README 기록**을 남긴다. 이력서에는 측정값이 있는 것만 쓴다.
- 특정 회사 도메인을 흉내 내지 않는다. 어느 공고에서든 자주 나오는 역량에 대응되게 만든다.
- 단계가 끝날 때마다 README, 포트폴리오, 이력서의 crypto-quant-lab 설명을 함께 갱신한다.
- 기존 백테스트·API는 그대로 동작해야 한다. 기존 테스트 113개는 계속 통과해야 한다.
- 작업 방식은 v1과 같다(`docs/PLAN.md` 3절): 최소 단위 커밋, 설계 노트 동시 갱신. 매일 `docs/ai-log.md`에 Claude Code에게 맡긴 것과 직접 확인·수정한 것을 기록한다.

## 2. 현재 상태 (v1)

- Django 5.2 + DRF, MySQL 8(Aiven), Redis(Upstash), Vercel 서버리스 + Cron, Sentry, Next.js 대시보드
- 5종목 일봉 약 13,700건, 테스트 113개, 무결성 규칙 6종, 멱등 upsert + 최근 7일 재수집
- 한계
  - 데이터가 1만 건대라 성능 튜닝·대용량 집계를 보여 줄 수 없음
  - 수집·백테스트가 요청 안에서 동기로 실행됨

## 4. 결정 사항

### 4.1 DB를 PostgreSQL로 전환 (main 브랜치)

- 전환 전 상태는 git 태그 `v1-mysql`로만 남긴다.
- 이유: 국내 백엔드 공고에서 PostgreSQL 요구가 많고, 튜닝 도구(EXPLAIN ANALYZE, BRIN, 부분 인덱스 등)를 보여 주기 좋다.
- **main에 push하면 Vercel이 바로 운영에 배포**한다. 따라서 main을 PostgreSQL로 바꾸는 날(D1)에 운영 DB도 함께 전환한다.

### 4.2 운영 DB: Neon (Vercel 마켓플레이스)

| 항목 | Neon 무료 | Aiven PostgreSQL 무료 |
|---|---|---|
| Vercel 연동 | 마켓플레이스 설치 시 환경변수 자동 주입 | 수동 설정 |
| 싱가포르 리전 | 있음 (`aws-ap-southeast-1`), 함수 리전 sin1과 맞음 | 고를 수 없고, Aiven이 바꿀 수 있음 |
| 저장 용량 | 프로젝트당 0.5GB | 1GB |
| 컴퓨트 | 월 100 CU-시간, 5분 쉬면 꺼졌다가 요청 시 자동으로 깨어남 | 시간 제한 없음 |
| 미사용 시 | 다음 요청에 자동으로 깨어남 | 서비스가 꺼짐(v1에서 실제로 꺼져 운영 500 발생, 2026-10-03) |
| 커넥션 풀러 | 있음 (PgBouncer, 트랜잭션 모드) | 없음, 동시 연결 최대 20 |

- 선택 이유: 자동으로 깨어남, 리전 고정, 풀러 제공.
- 한도를 넘으면 요금이 청구되지 않고 DB가 멈춘다. `/status`에서 사용량을 확인한다.
- 마켓플레이스 설치 때 무료 플랜 선택·카드 요구 여부를 확인한다. 카드를 요구하면 Neon에 직접 가입해 연결 주소만 Vercel 환경변수에 넣는다.

### 4.3 데이터 규모 분리

| 위치 | 분봉 | 용도 |
|---|---|---|
| 로컬 Docker PostgreSQL 18 | 5종목 × 1년 (약 263만 행) | 대용량 적재·집계·튜닝 측정 |
| 운영 (Neon) | 최근 30일 (약 21.6만 행, 약 60MB) + 집계 결과 | 서비스 |

README에 "측정은 로컬, 데이터 규모 N건"을 명시한다. 1년치를 운영에 올리면 0.5GB를 넘을 수 있으므로 올리지 않는다.

## 5. 설계 시 주의점 (v1 코드 확인 결과)

| # | 확인한 것 | 대응 |
|---|---|---|
| 1 | MySQL 전용 코드: `config/__init__.py`(PyMySQL), `base.py`의 `OPTIONS={"charset": "utf8mb4"}`, `prod.py`의 `ssl.ca` 임시 파일 | 제거하거나 교체한다. psycopg는 `charset` 옵션을 받지 않는다. SSL은 URL의 `sslmode=require`로 대신한다. `psycopg[binary]`는 wheel로 설치돼 Vercel 빌드 문제가 없다 |
| 2 | `upsert_candles`가 이미 `supports_update_conflicts_with_target`로 DB에 따라 분기함 | PostgreSQL에서는 `ON CONFLICT (asset, date)`로 동작한다. 분봉 upsert도 같은 구조로 만든다 |
| 3 | 운영의 `IntegrityIssue.note`(사람이 해결 처리한 기록), CollectionRun 이력 | 다시 백필하면 사라진다. `dumpdata` → `loaddata` → `sqlsequencereset` 순서로 옮긴다 |
| 4 | `data_version()`은 DailyCandle의 `Max(collected_at)` | 분봉·집계 재처리는 백테스트 캐시를 바꾸지 않는다(백테스트는 일봉만 씀). 캐시 무효화 확인은 일봉 재처리일 때만 한다. 바뀐 행이 0건이면 덮어쓰지 않아 `collected_at`이 괜히 바뀌지 않게 한다 |
| 5 | 동시 실행 방지 | `pg_advisory_xact_lock`은 기다린다. 바로 409를 주려면 `pg_try_advisory_xact_lock`을 쓴다. 트랜잭션 단위 락이라 PgBouncer 트랜잭션 모드에서도 안전하다(세션 단위 락은 깨진다) |
| 6 | 업비트 일봉은 UTC 00:00(KST 09:00)에 시작 | 분봉 `ts`를 UTC로 저장하면 `date_trunc('day', ts)`가 일봉 경계와 정확히 맞는다 |
| 7 | 백필은 200개씩 과거 방향으로 받음 | 물리적 저장 순서가 시간 역순·종목별로 나뉜다. BRIN 비교 때 `pg_stats.correlation`을 같이 기록한다 |
| 8 | 서버리스 함수 기본 제한 300초 | 재처리 API는 기간 상한(예: 분봉 31일)을 두고, 긴 기간은 management command로 실행한다 |
| 9 | Neon 풀러는 트랜잭션 모드 | 앱은 `-pooler` 주소, `migrate`·`loaddata`는 직접 주소를 쓴다. `DISABLE_SERVER_SIDE_CURSORS=True` |

규모 추정: 1년 분봉 백필은 약 13,000회 요청이고, 초당 약 8회면 30분 안팎 걸린다(거래가 없는 분은 업비트가 주지 않아 실제로는 조금 적다).

**완료 기준:** 시나리오별 전후 수치와 "왜 이 인덱스를 골랐는지" 설명이 문서에 있음

### D6 — 운영 콘솔 + 관측성 + 운영 반영

- [ ] 대시보드 `/ops`: 종목×날짜 매트릭스(수집 완료/분봉 부족/집계 안 됨/정합성 이슈), 칸을 누르면 그날 상세와 재처리 이력

## 7. 2단계 — 데이터 계약 + AI 기능 (각 1~2일)

### 데이터 계약 + Parquet + 오브젝트 스토리지

- [ ] pandas 분석 작업(일별 변동성·거래대금 지표)이 결과를 Parquet로 출력
- [ ] `contracts/*.json`에 컬럼·타입·nullable·단위·스키마 버전 정의, 적재 전 검증, 위반 시 적재 거부 + 이슈 기록
- [ ] 분봉 원본을 Parquet로 S3 호환 스토리지에 보관하고 DB에는 최근 데이터·집계만 유지(후보: Cloudflare R2, Vercel Blob — 시작 때 무료 범위 확인)
- [ ] 계약 버전이 바뀔 때 API 응답 호환을 지키는 방법 문서화
- 오케스트레이터(Prefect·Airflow)는 서버리스에서 못 돌리므로 로컬 flow 예시만 둔다.

### LLM 대화형 분석

- [ ] 질문(예: "지난주 BTC 거래대금이 가장 컸던 시간대는?") → 에이전트(LangGraph) → 기존 집계 API만 tool로 호출 (LLM이 SQL을 직접 만들지 않음)
- [ ] 답변에 근거 숫자와 조회 기간 표시, 기간·종목 입력 검증, 최대 단계 수 제한
- [ ] 평가 세트 15개 정도로 정답률 확인, 요청별 토큰·지연·비용 기록
- [ ] API 키는 서버 환경변수에만 둠, 공개 데모는 요청 제한 강화
- 프레임워크는 LangGraph로 정한다. 국내 AI 기능 공고에서 자주 요구하고, 최대 단계 수 제한(`recursion_limit`)과 입력 검증·답변 근거 확인을 그래프의 노드로 드러낼 수 있다. 모델·제공자는 2단계 시작 때 정한다.

## 8. 3단계 — 운영 안정성·확장 (필요할 때 골라서)

- [ ] Cron 미실행 자동 알림(하트비트) — 예: GitHub Actions 예약 실행으로 `/status` 확인
- [ ] 비동기 작업: 재처리·대량 백필·파라미터 그리드 탐색을 큐로 분리. 로컬은 Celery, 운영은 서버리스에 맞는 방식(예: Vercel Queues) 검토. CollectionRun의 `beat` 선택지도 이때 실제로 쓰거나 정리
- [ ] 백테스트 체결 옵션: 다음 날 시가 체결, 슬리피지 분리
- [ ] 대상 확장: 종목 추가 또는 다른 거래소 — 같은 수집·정합성 구조가 다른 소스에도 그대로 쓰이는지 보여 주기

## 9. 하지 않을 것

- 특정 회사 도메인을 억지로 흉내 내기 (예: 형식만 있는 멀티테넌트 권한 구조)
- 유료 도구 도입 (Datadog 등 — Sentry와 자체 지표로 설명)

## 10. 지원할 때 쓰는 방법

레포는 하나로 두고, 공고에 맞춰 이력서·포트폴리오에서 앞세울 부분만 바꾼다.

| 공고 성격 | 앞세울 부분 |
|---|---|
| 데이터 집계·분석 API 백엔드 | 집계·재처리, 정합성 대조, 쿼리·인덱스 튜닝 수치 |
| 데이터 수집·배치·ETL | 대량 수집·멱등 upsert, 재처리, 데이터 계약·Parquet |
| 운영·관측성·모니터링 | 운영 콘솔, 쿼리 지표, 하트비트 알림, 트러블슈팅 기록 |
| AI 기능 개발 | LLM 대화형 분석, 평가 세트·비용·지연 기록 |
| 금융·퀀트·가상화폐 | 백테스트, 미래참조 방지, Decimal 처리 |

## 11. 면접 포인트

- 분봉과 일봉의 "결측" 정의가 다른 이유와 정합성 규칙을 다르게 둔 이유
- 재처리를 dry-run → 실행 → 재검증으로 나눈 이유, 멱등성과 동시 실행 방지(advisory lock, try 버전을 고른 이유)
- 인덱스 선택: 복합 인덱스 컬럼 순서, BRIN vs B-tree, 부분·커버링 인덱스의 근거와 측정값
- keyset 페이지네이션으로 바꾼 이유
- 서버리스에서 DB 커넥션을 다룬 방법 (풀러 트랜잭션 모드의 제약)
- 집계를 DB에서 할지 pandas에서 할지 나눈 기준
- LLM에게 SQL 대신 기존 API만 tool로 준 이유, LangGraph로 단계 수·검증을 제어한 방법
- MySQL에서 PostgreSQL로 옮기며 바뀐 점 (GCMS의 SQLite → PostgreSQL 전환 경험과 연결)
- v1 포인트: 미래참조 방지, Decimal/float 구분, 캐시 키에 데이터 버전 포함, 서버리스 Cron 트레이드오프
